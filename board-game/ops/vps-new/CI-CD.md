# CI/CD plan for the isolated new VPS

This is a test-only deployment path. Do not edit/reuse the active production workflow or `scripts/deploy-vps.sh`; those are pinned to `103.9.78.75`, `/home/nhat_hoang/co-tuong/board-game`, `/var/www/cotuong`, current production database/backup hooks and `hovanggame.com` health checks.

## Prepared release contract

`build-test-release.sh <40-character SHA>` runs on a CI runner checked out at that SHA. It confirms the commit is reachable from `origin/master`, refuses tracked environment files other than `.env.example` and admin-access files, installs the lockfile dependencies, runs typecheck/tests/build, archives the tracked `board-game/` project plus generated `dist` and `node_modules`, and adds the shared upload symlink at `/srv/cotuong/shared/uploads`. The packager uses `umask 027` and a `2750` release root so the `cotuong_release` runtime group can read/traverse code without write access. `verify-test-release.py` rejects missing runtime files, credential files, unsafe paths/symlinks, and group/world-writable entries. `.env.example`, ignored engine binaries, and other local files are not packed.

`.github/workflows/vps-test-release.yml` builds an immutable SHA-addressed artifact and checksum behind the `vps-test` reviewer gate. `.github/workflows/vps-test-deploy.yml` is a separate manual `workflow_dispatch` path; merge does not trigger deployment. It verifies the selected full SHA is on `master` and has a successful push CI run, validates the Environment reviewer/branch/no-admin-bypass policy before referencing it, builds and verifies the archive, then pauses at `vps-test` approval before deployment secrets are available. The deploy client pins host `103.153.254.184` and user `cotuong_deploy`, verifies the `known_hosts` secret (never TOFU), uploads only the checksum-verified archive, extracts into a unique staging directory, validates owner/group/layout/permissions, checks the enabled systemd unit is fixed to `cotuong`, Node 22.23.3, and loopback `127.0.0.1:3001`, refuses deployment if Nginx is active, creates the SHA pending symlink, and invokes only `sudo -n /usr/local/sbin/cotuong-deploy-activate` with no arguments. The restricted deploy user cannot traverse `/etc/cotuong`; the root activation helper validates `cotuong.env` owner `root:cotuong` and mode `0640` before changing `current`. The deploy workflow does not read or expose that file. It does not run `npm ci` or database migrations on the VPS.

`.github/workflows/vps-test-preflight.yml` is a separate manual, read-only path behind the same Environment approval. It uses the Environment-scoped SSH secrets and strict pinned host key to check the deploy identity, private incoming directory, release tree, service unit, sudo allowance, Nginx state, and current/pending pointers. It never uploads files, runs the activation helper, or starts/stops/restarts services. Run this before the deployment workflow so directory and SSH permission failures are found without authorizing a release.

The activation helper is installed `root:root` mode `0750` by design. The deploy user must not execute that file directly; it may request only the exact no-argument helper through its restricted `NOPASSWD` sudo rule. Therefore preflight checks file owner/mode and `sudo -n -l` permission, and must not require `test -x` as the unprivileged deploy user.

For a clean first boot, `install-app-unit` may install and enable the reviewed unit when `current` is absent, but it never starts the service. The first approved manual deployment creates `current` and restarts the service only after the release is complete. If `current` already exists, the helper requires it to resolve to a complete release under `/srv/cotuong/releases`.

The deployment health check is process/API liveness plus an Engine.IO polling handshake; `/api/health` does not query MySQL and the handshake does not authenticate a player. Bootstrap creates an empty `cotuong_stage` and app/migrator accounts but deliberately does not apply SQL. Before the first deployment, an operator must review and apply the current migrations using the protected migrator configuration, then run `db:verify` using the application account. Do not treat a green liveness check as proof that the schema is ready. DDL has implicit commits; take and verify the approved test-database backup first, and inspect/recover manually if migration stops partway. Neither workflow migrates or rolls back database state.

`prepare-test-vps-first-boot.ps1` is the one-time interactive administrator step after this change is merged. It pins the host and ED25519 fingerprint, uploads a unique private bundle, verifies SHA-256 and Bash syntax, then requests sudo only in the local PowerShell terminal. SSH/SCP receive a temporary `-F` config file containing `StrictHostKeyChecking yes` and the quoted `UserKnownHostsFile` path; this avoids Windows PowerShell 5.1's legacy native-argument handling stripping embedded quotes from `-o UserKnownHostsFile="..."`. Run `-Preflight` first to exercise the same SSH and SCP config read-only (remote identity/IP plus `/etc/hostname`, copied locally). The wrapper removes its local staging directory recursively without confirmation and cleans only its unique remote staging directory. Its root script backs up and atomically updates the two fixed helpers and unit template, creates only the empty `cotuong_stage` schema and scoped app/migrator accounts with generated passwords, writes root-protected environment files, and installs/enables the unit without starting it. The app account gets DML only; the migrator gets DML plus CREATE/ALTER/INDEX/REFERENCES. It does not run migrations, create `/srv/cotuong/current`, start the service, activate a release, enable Nginx, or change DNS/firewall. A failure after MySQL provisioning is fail-closed and requires inspection before rerunning.

The root-owned activation helper accepts no arguments/environment. It validates the pinned host IP, release SHA/path/owner/group and required files, rejects environment/admin-access files, atomically switches `/srv/cotuong/current`, restarts only `cotuong-test.service`, checks `http://127.0.0.1:3001/api/health`, and restores the prior symlink/service if health fails. CI simulates a healthy activation, rollback to an old release, and failed first activation with temporary paths and mocked host/systemd commands. It never modifies MySQL or deletes old releases. A first deploy with no previous release stops the service and removes `current` if health fails.

## GitHub configuration required later

Both workflows are deliberately separate from the production workflow and `scripts/deploy-vps.sh`. Third-party actions are pinned to reviewed full commit SHAs. Deployment secrets are Environment-scoped (`VPS_TEST_SSH_KEY`, `VPS_TEST_KNOWN_HOSTS`) and never enter the package job or artifact. Generate/install the key out-of-band; keep its private half out of the repository, PowerShell history, chat and logs.

## Deliberate gates

- Before the first deployment, run the manual read-only `VPS test read-only preflight` workflow and require it to pass. Bootstrap has installed the test unit and protected environment files and created the empty test schema/users; the service remains stopped and `/srv/cotuong/current` is absent. No release has been activated.
- Bootstrap reports the least-privilege test schema/users and protected environment files created, but privileged grants/schema and environment-file metadata have not yet been independently re-read. The deploy workflow performs no migration. Review/apply migrations only to `cotuong_stage`, then run `db:verify` with the app account before first activation. Do not point this Environment at production data.
- Activation health failure switches the code pointer back to the previous release; on a first deployment it stops the service and removes `current`. It never changes database state or deletes previous releases. Database migrations are intentionally outside the code rollback path.
- The deployment health checks cover process/API liveness and a Socket.IO polling handshake over loopback. They do not yet exercise authenticated matchmaking/gameplay; that requires a verified test schema, credentials, and test account.
- The bootstrap only creates an empty schema and credentials. The first deployment must wait for the reviewed migrations and a successful `db:verify`; current deployment automation intentionally does not apply migrations or verify schema through the liveness endpoint.
- Existing app code expects Fairy-Stockfish and Pikafish Linux assets. Fairy release compatibility, license notice and pinned checksum are not established in this repository; deployment can run, but engine play should remain disabled until that asset is reviewed and smoke-tested.
- This path does not alter firewall, DNS, TLS, external backups, GitHub production secrets or data on the old VPS. It does not enable public Nginx; health checks stay on loopback via SSH.
