# Encrypted offsite backups for the test VPS

## Layout and trust boundaries

- The local source is a paired SQL dump and media archive in `/var/backups/cotuong-stage`, each root-owned `0600` with SHA-256 sidecars in a root-owned `0700` directory. The media allowlist is `group-avatars/` and `message-images/`; other files or symlinks fail closed.
- `cotuong-local-backup.service` starts `cotuong-offsite-backup.service` after local success. The offsite unit is skipped until `/etc/cotuong/offsite-backup.conf` exists. The admin installer requires R2 config and reviewed tools, installs units, and leaves the local timer disabled; it accepts an existing root:root `0700` backup directory and never removes existing backup files.
- The upload helper encrypts the compressed dump, media archive and manifest with `age`. The manifest binds source and ciphertext hashes plus media file count. The VPS stores only public age recipients. Keep the matching private identity off the VPS and outside GitHub.
- Use a bucket-scoped R2 S3 credential in `/etc/cotuong/r2-credentials`, a read-only Cloudflare API token for lock inspection in `/etc/cotuong/r2-read-token`, recipients in `/etc/cotuong/r2-age-recipients`, and non-secret endpoint/account/bucket variables in `/etc/cotuong/offsite-backup.conf`. Each file must be `root:root 0600`; none belongs in the app environment.
- The non-secret systemd environment file contains only `COTUONG_R2_ACCOUNT_ID`, `COTUONG_R2_BUCKET`, and `COTUONG_R2_ENDPOINT`. The S3 credentials file uses an AWS shared-credentials `[default]` profile with Object Read & Write scoped to the dedicated bucket. Object tokens cannot read bucket configuration. Lock/lifecycle inspection uses Cloudflare Admin Read only through the REST API; this permission is account-wide and can read/list objects and view configuration across the account. Do not provide that token to the VPS unless the operator explicitly approves the broader read scope. Never use Admin Read & Write. If this scope is not approved, the uploader remains blocked because it fails closed without lock/lifecycle verification.
- R2 object names are random, under `cotuong-stage/`. Each `PutObject` uses atomic `If-None-Match: *`; the helper refuses unsafe HEAD errors and never overwrites/deletes remote objects. SQL, media and manifest ciphertexts each have SHA-256 sidecars. The helper downloads all six objects again and verifies their SHA-256 before printing `OFFSITE_VERIFIED`.
- Every upload fails closed unless the Cloudflare API confirms an enabled 30-day lock on the exact `cotuong-stage/` prefix and no overlapping lifecycle deletion rule. Cleanup uses `prune-test-r2-backups.py`, whose default is dry-run; it verifies all object/sidecar checksums, requires the latest successful upload marker, removes only complete sets older than 30 days, and always preserves the newest verified set. Deletion requires both `--apply` and `COTUONG_R2_RETENTION_APPLY=1`. The bucket-scoped Object Read & Write credential can delete objects after the lock expires, so keep cleanup approval separate and monitor its protected logs.
- Local backups older than 12 hours are rejected. An offsite systemd failure is not a completed two-site backup; monitor `cotuong-offsite-backup.service` and require its successful `OFFSITE_VERIFIED` record alongside the local backup checksum.
- No local backup is automatically deleted by this path. Retain local files until a separate approved cleanup policy is selected; monitor VPS free space. R2 lifecycle deletion must not overlap `cotuong-stage/`; use only the reviewed scoped retention helper after its separate approval.

## Offsite verification and restore

Run `verify-offsite-test-backup.py <prefix> <bucket> <endpoint> <local-age-identity>` on a trusted operator computer with the age private identity and R2 read credentials available locally. It downloads ciphertext and SHA-256 sidecars to a private temporary directory, verifies hashes, decrypts the dump/media/manifest, checks both source hashes, validates gzip and the media archive allowlist, then removes the temporary files. It never sends the private age identity to the VPS.

This proves that the external copy is readable, decryptable, and byte-valid. It does not claim a database restore. For a full offsite restore drill, transfer only the decrypted **test** dump to the VPS through a protected temporary channel, verify it against the encrypted manifest's `source_sha256`, set root ownership/mode `0600`, and run the existing `validate-test-backup.py` scratch-schema validator. Obtain explicit operator approval before that VPS/database operation. Preserve the original local backup and all R2 objects.

No Cloudflare account, bucket, credentials, bucket lock, lifecycle rule, or VPS package/unit configuration is created by this code change. Those are explicit setup operations requiring approval. The first setup must use a dedicated private bucket and confirm that public access is disabled.

## Operator setup requiring separate approval

1. **Cloud/billing approval:** in Cloudflare, activate R2 only after reviewing billing, then create a dedicated Standard bucket (suggested name `cotuong-stage-backup`). Select the default jurisdiction: this helper deliberately accepts only `https://<account-id>.r2.cloudflarestorage.com`, not jurisdictional endpoints. Keep the public development URL disabled and add no custom domain. Record only the bucket name/account ID/endpoint in the non-secret setup record.
2. In bucket settings, add an enabled age lock on prefix `cotuong-stage/` for 30 days (`2592000` seconds). Do not add a lifecycle deletion rule that overlaps this prefix; the uploader rejects it so deletion remains governed by the tested helper that preserves the newest verified set. Review broader and nested rules too. These policy changes need approval and the administrator credential stays off the VPS.
3. Create an R2 Object Read & Write S3 token scoped to this bucket only. Save its Access Key ID and Secret Access Key in a password manager; do not paste them into chat, command arguments, history, GitHub or app env. Create a separate Admin Read only API token for policy inspection. Cloudflare's Admin read token is account-wide; record that decision before provisioning. A restore-only operator token should be Object Read only for this bucket.
4. On the trusted operator computer, generate an age identity using `age-keygen`. Keep the private identity in a private user directory with verified OS ACLs and an independent offline recovery copy. Export only the `age1...` public recipient for the VPS. Losing the private identity makes R2 backups unrecoverable. Windows `chmod` alone does not establish a private ACL.
5. **VPS configuration approval:** install reviewed age/AWS CLI versions and update the root-owned bundle through a separately reviewed operator step. Prepare the four files below interactively with root ownership and mode 0600; refuse existing paths rather than overwriting credentials. No credential is printed or supplied in shell command arguments. Do not enable any timer or run backup/upload as part of configuration.

| File | Contents |
| --- | --- |
| `/etc/cotuong/offsite-backup.conf` | Three non-secret assignments: account ID, bucket, global endpoint |
| `/etc/cotuong/r2-credentials` | `[default]` with `aws_access_key_id` and `aws_secret_access_key` from the bucket-scoped object token |
| `/etc/cotuong/r2-read-token` | The Admin Read only API token, one line |
| `/etc/cotuong/r2-age-recipients` | Public age recipient(s), one per line; no private identity |

6. Approve the first upload separately after read-only config/policy validation. The passed local dump is never modified. If it is older than 12 hours, approve a fresh local backup/drill first. Require `OFFSITE_VERIFIED`, then an off-VPS decrypt/checksum/gzip verification and an approved scratch MySQL restore using a downloaded R2 copy before calling the two-site system complete. Retain any partial remote upload on failure; it is not a successful backup and must not be automatically deleted or retried as a DB operation.
7. Approve timer activation only after the manual two-site drill passes. The installer installs helpers and units, runs `systemctl daemon-reload`, and deliberately leaves the timer disabled. After separate approval, enable it with `sudo systemctl enable --now cotuong-local-backup.timer`; verify the next trigger with `systemctl list-timers cotuong-local-backup.timer`. The timer runs daily at 03:00 Vietnam time with `Persistent=false`, so it does not catch up after downtime. Enabling it authorizes future real database/media backups and R2 uploads.

References for credential scope: [R2 authentication](https://developers.cloudflare.com/r2/api/tokens/), [REST vs object token limitations](https://developers.cloudflare.com/r2/platform/troubleshooting/), [read lifecycle API](https://developers.cloudflare.com/api/resources/r2/subresources/buckets/subresources/lifecycle/methods/get/).

## Cloudflare R2 policy and expected cost

Use a private R2 Standard bucket. Set an enabled 30-day age lock (`2592000` seconds) on `cotuong-stage/`, and do not configure lifecycle deletion for this prefix. The guarded helper can delete complete sets after 30 days only following separate approval, and always preserves the newest verified set. Current published pricing includes 10 GB-month and operation allowances; Standard storage above that is `$0.015/GB-month`, and direct R2 egress is free. Verify current billing and jurisdiction before creating the bucket.

References: [R2 pricing](https://developers.cloudflare.com/r2/pricing/), [R2 bucket locks](https://developers.cloudflare.com/r2/buckets/bucket-locks/), [R2 object lifecycles](https://developers.cloudflare.com/r2/buckets/object-lifecycles/), [R2 conditional writes](https://developers.cloudflare.com/r2/api/s3/extensions/).
